03The spine

One invariant everything else bends to

Plain files are the only store. No parallel database, ever.
  • Recorded three separate times — ADR 0004, 0020, 0024 — because it keeps being the thing that decides an argument.
  • The consequence people misremember: the rule was never "the UI is read-only." It was "there is no second store." That distinction is exactly why the Cockpit could grow from a viewer into a read-write orchestrator (ADR 0032) without breaking anything — it writes the canonical task file, not a shadow copy of it.
  • Everything in this talk is a consumer of the same bytes: the agents, your editor, git, the retrieval index, and the browser UI.
  • Practical payoff: a change to the AI's memory is a git diff you can review in a PR. There is no "export the knowledge base" problem, because there is nothing to export.
This is the spine of the whole talk — every later design choice traces back here. The read-only-vs-no-second-store distinction is worth landing carefully, because a senior engineer who knows the earlier ADRs will otherwise think we regressed our own decision. We didn't: 0020's read-only was a consequence of the rule, not the rule. And for the managers: no database means no migration, no backup story, no vendor. The knowledge base is just files in your repo.

05Part 1 · Memory

The log is not a changelog — it is an ABI

## [YYYY-MM-DD] {operation} | {title}          ← locked prefix (ADR 0006)

Context / Created / Modified / Deleted / Decision
  • Why locked: grep "^## \[" log.md | tail -5 returns the wiki's recent history as a clean timeline — with no Markdown parser anywhere.
  • It is a parser contract, not a style guide. The server splits on /^## \[(\d{4}-\d{2}-\d{2})\]\s+(\S+)[^\n]*$/m. The trailing [^\n]*$ is load-bearing: it swallows the title so page names inside it never get harvested as touched pages.
  • Staleness falls out of it for free. A page is stale when a newer ingest entry named it but the page's own verified || updated predates that ingest. That single rule is the Cockpit's stale-wiki badge.

Say it before they find it

  • Change the prefix and staleness detection silently stops working. Nothing errors — the log just becomes unparseable.
  • The declared vocabulary is ingest · lint · query · restructure, but the seeded first entry uses init and the audit skill writes audit. Nothing validates the verb. The parser only filters for ingest, so the others are inert rather than broken.
  • Staleness is computed over top-level pages only — nested pages and adr/ never raise the flag.
This is the first slide where engineers lean in. The idea worth selling: a convention becomes valuable the moment code depends on it, and dangerous for exactly the same reason. We locked a Markdown heading format so that grep is a valid query engine over history — and then two pieces of production code came to depend on that lock. The regex detail with the trailing wildcard is the kind of thing that signals this was written by someone who hit the bug. And own the vocabulary drift: we documented four operations and ship five verbs. Nobody validates it because nothing reads it.
06Part 1 · Memory

The write path: draft the log first

One role writes the wiki — the Ingester — and its procedure inverts the obvious order. A single ingest routinely touches 10–15 pages.
Step 2 · Plan

Search, then dedupe, then map coverage

Retrieval-first discovery, then one wikilink hop. Append-vs-mint: only mint a page if the topic is a distinct first-class noun and appending would overflow the host — never mint a near-duplicate. Coverage map: every file in the task log's files: list must land on a page, or carry an explicit no wiki impact: {file} — {reason}.

Step 3 · The inversion

Draft log.md before touching a page

The entry is written and shown to the user before anything is applied — so the audit record and the approval artifact are the same object. If the plan is wrong, you edit the draft, not the pages.

Step 4 · Apply

Mechanical flows, semantic asks

A moved file or a version bump applies directly. Changed conclusions or a rewritten section show a diff first. And a resolved contradiction must be written into the page body — a contradiction resolved only in the log is an incomplete ingest.

Three ask-points

  • a new page
  • a page or section deletion
  • a semantic rewrite of an existing page

Routine updates flow without asking. A rejection is recorded verbatim as user rejected: {reason}.

Step 10 · Close out

  • Task folder moves active/ → completed/, status INGESTED. Raw moves to raw/archived/ — never deleted.
  • Run the structure checker, fix findings on the pages just written, then re-index.
The headline is the inversion: draft the log entry before you touch anything. Most systems write the audit record after the fact, which means the audit record can lie. Here the record IS the plan, so it cannot drift from what was proposed — and the human approves the plan by approving the record. Two details worth calling out: the coverage map turns "did we capture everything from that task?" into a mechanical checklist over the files the coder actually touched; and the rule that a contradiction resolved only in the log is an incomplete ingest, because the next reader reads the page, not the log.

The pull digest is instruction-carrying Raw. The hook doesn't just dump git log. It writes a three-part contract into the file — what changed (into page bodies), cross-project impact or an explicit "no cross-project impact — why", and a plain-language summary — plus a grep for contract-shaped paths (lockfiles, .proto, openapi, migrations/, shared packages) so ripple is flagged rather than guessed. The row that matters for the value story is the chain: the pipeline deliberately terminates at the Ingester, so finishing a task and updating the project's memory are the same event. The pull-digest row is the one people find surprising — a git pull becomes a memory event. And note the design of the digest: it carries its own instructions, because we assume the agent reading it has no other context. That contract is duplicated in three places — the hook, the skill, and the orchestrator's prompt — which is either resilient or redundant depending on how much you trust agents to read context. We chose resilient.

09Part 1 · Memory

Deterministic vs judgement — and why we moved the line

Code decides — one pure function, 22 tests

  • required frontmatter · kebab-case filename
  • section size against the ~900-token chunk target
  • broken wikilinks · ambiguous wikilinks (a slug collision is surfaced, never silently misresolved)
  • orphans · reachability from index.md

Three consumers, one implementation: the doctor command, the Ingester's write-time gate, and Lint — which is told to fold the findings in verbatim, "do not re-derive them by eye."

The LLM still judges

  • contradictions between pages
  • is this concept worth its own page?
  • synonyms · near-duplicate pages
  • a contradiction resolved in the log but never applied to the page

Mechanising this half was considered and rejected: a structure checker guarantees retrievable structure. It does not judge meaning.

Why this exists at all: before it was code, nine of ten mechanical checks lived only in prose — an LLM re-derived them from a document on every lint. The shipped scaffold itself had drifted: an off-taxonomy tag and a dangling wikilink, unnoticed. The spec was the enforcement, and the spec drifted.
Three qualifiers we say out loud: the chunk "token" count is characters ÷ 4, not a tokenizer, and it only warns when the long section has no sub-heading to split it. There is exactly one fail-level finding in the whole checker — a missing root index.md — so fifty warnings still exit zero. And an empty wiki short-circuits to zero findings, which means "clean" and "nothing there" print the same line.
This is the slide senior engineers came for. The argument: mechanical checks belong in tested code, and tokens should only be spent on semantics. The evidence that it was needed is that our own shipped scaffold had drifted while the prose spec was supposedly enforcing it. Then immediately undercut yourself with the three qualifiers, because someone will read the source: chars-over-four is not a tokenizer, the gate can only fail on one thing, and an empty wiki looks identical to a healthy one. Saying all three yourself is the difference between a checker you trust and a checker you oversold.
10Part 2 · Substrate

"The Karpathy method" — pinned down, not name-dropped

Borrowed terms rot. This one has its own entry in a section literally called Flagged ambiguities, because it was being used loosely and that counted as a defect in the project's own language.
What it means here

Five concrete commitments

A flat directory of atomic pages · Obsidian frontmatter · heavy [[wikilinks]] · a Map-of-Content index.md as the single entry point · an append-only log with a greppable locked prefix.

Where it actually came from

Reverse-engineered, not adopted

The structure was derived from two real wikis the author already ran — which turned out to be flat Obsidian directories. The reference template's 21 pre-created pages were dropped because neither real wiki had them, and confidence / source_count / related_sources were dropped as aspirational fields nobody filled in.

This is the answer to "isn't that just an appeal to authority?" — no: the gist supplied the vocabulary, real usage supplied the shape, and the parts of the gist that didn't survive contact with a real wiki were deleted. Five anchor pages ship, three of them honestly declared status: stub; everything else is born during an ingest, when a topic actually demands a page.
Expect the appeal-to-authority challenge — it's the fair one. The defence is that we didn't copy a gist, we checked it against two working wikis and threw away the two-thirds that had never been used. That's the same evidence-first posture as everywhere else in the tool. And be precise if pushed: we do ship five starter pages, three marked stub. What we rejected was pre-creating twenty-one speculative topic pages, because empty stubs with confident frontmatter actively mislead an AI about what is known.

12Part 2 · Substrate

Why Obsidian: the argument is a constraint, not a feature

  • Obsidian's file tree hides dotfiles. So the workspace ships no dotfiles inside it: tasks/.weekly became tasks/weekly, raw/.archived became raw/archived, and .gitignore moved out to the project root entirely.
  • A UI affordance drove a filesystem convention across the whole tool. That is a real design constraint flowing from a tool choice — not decoration.
  • .obsidian/ is the single sanctioned exception, accepted only because the application owns that name.
  • Tracked vs ignored encodes a distinction most teams get wrong: shared taste — plugins, hotkeys, themes — is versioned; per-user window state — pane layout, graph camera, cache — is not. Four ignore lines.
  • Install offers a non-hidden tcgstackflow → .tcgstackflow symlink (default yes) because the vault picker hides dotfiles too. Declining is fine; failure prints a Windows hint and moves on.

The counter-argument — conceded

"This is just Markdown files. Obsidian is optional."

Correct. That is the design.

  • The templates ship no .obsidian/ directory — the app creates it on first open.
  • grep -rn obsidian across the entire Cockpit returns nothing. An earlier ADR promised an "Open in Obsidian" link; it was never built.
  • A team that never installs Obsidian loses the graph view and nothing else.

"Obsidian-flavoured" is a format commitment — YAML frontmatter, [[wikilinks]], flat directory — not a tool dependency. The format is the interop contract; the app is a viewer.

Lead with the constraint, because it's the least obvious and most credible argument. Most people justify Obsidian with "graph view is nice." The real evidence that the choice is load-bearing is that it changed our directory naming everywhere — we banned dotfiles inside the workspace because they'd be invisible in the vault. Then concede the counter-argument completely and on purpose: zero lines of Cockpit code know Obsidian exists. That concession is the strongest form of the argument — we committed to a format, not a vendor, and the format is what every other tool reads.

  • Two stages, two different jobs. Search supplies recall — which of 200 pages match this phrasing. The graph supplies bounded expansion — what the author knew was adjacent. Drop the graph and you bet everything on embedding recall; make it transitive and you blow the budget the design exists to protect.
  • One hop is a token budget, stated as one. Default eight hits, open only the pages you will actually use, and never read every page "to be safe."
  • The graph is mechanically checked: a broken link is flagged as "a dead end for one-hop reading"; a slug collision across directories surfaces as an ambiguous link rather than a silent wrong jump; orphans and unreachable-from-index.md are separate detectors, because connectedness and reachability are different health properties.
  • Rename hazard: a rename without an aliases: entry breaks retrieval and backlinks at the same time. That is why aliases are in the schema.
Real drift, found while preparing this talk: the one-hop rule appears in all six agent profiles and in two of the three tool adapters. The Codex adapter mandates search-first but drops the one-hop clause. That is a bug, not a design choice — and it is exactly the class of thing the workspace audit is supposed to catch.
The point: the wikilink graph is not a visualisation feature, it is the second half of the retrieval algorithm. Search is statistical and will miss things; the graph is authored and encodes what a human knew was related. Neither alone is enough, and the one-hop bound is what stops the second stage from degenerating into "load the whole wiki." Close with the drift we found — it is honest, it's small, and it demonstrates that the audit tooling has real work to do. Never claim a protocol is uniform without grepping first; someone in the room will.
14Part 3 · Retrieval

Why a second layer on top of a perfectly good wiki

A Map of Content is a curated tree. A curator cannot anticipate every future phrasing.
A page about token refresh is invisible to the question "why does the session drop after an hour" — unless somebody happened to link them.

That is a recall failure, and it is structural: it gets strictly worse as the wiki grows. So there are three different questions, and three different things answer them.

LayerAnswersProperties
index.mdWhat exists, and how is it organised?Curated · always current · zero staleness risk · free
qmdWhich of these 200 pages matches my phrasing of this question?Statistical · can be stale · ~2 GB of local models · needs re-indexing
[[wikilinks]]What is adjacent to this page?Authored · bounded to one hop · encodes human judgement
Replacing index.md with search entirely was considered and explicitly rejected: it discards the curated graph the Ingester maintains and trusts a sometimes-stale index as the only way in. Collapse any two of these rows and you lose something real.
Frame this as recall, not convenience — otherwise it sounds like we added search because search is nice. The token-refresh example is the whole argument in one line: a curated tree encodes the questions the curator anticipated, and the useful questions are the ones nobody anticipated. Then be careful not to overclaim the other way: search is statistical and can be stale, the map is curated and never stale. Keeping both is the decision, and we wrote down the rejection of "just use search" so nobody re-litigates it in six months.
15Part 3 · Retrieval

How qmd works

Local hybrid retrieval — SQLite with FTS5 and sqlite-vec, three GGUF models via node-llama-cpp, 2.1 GB on disk. Every constant below read out of @tobilu/qmd@2.5.3 on this machine, not from the README.

01
BM25 probe

Try the cheap thing first. A strong keyword hit skips the LLM expansion entirely — unless you passed an intent:, which disables the bypass.

02
Expand

Otherwise a 1.7B model turns 1 query into 4: the original, a lex:, a vec:, and a hyde: hypothetical answer.

03
Fuse

BM25 + vector kNN per query, then RRF at k = 60. The original query's two lists get 2× weight; expansions stay at 1×.

04
Rerank

Top 40 candidates → best chunk per doc → a 0.6B cross-encoder. It reranks chunks, never full bodies.

05
Blend

By RRF rank: ≤3 → 75/25, ≤10 → 60/40, else 40/60. Source comment: "top retrieval results get more protection from reranker disagreement."

qmd query — hybrid, the default every agent leads with · qmd search — BM25 only, for known identifiers · qmd vsearch — pure semantic. Plus a typed query grammar: lex: / vec: / hyde: / intent:.
CHUNK_SIZE_TOKENS = 900, with a 200-token window, split on scored heading break-points. The refine rule is "switch verbs before you retreat to index.md."
The write side is coupled to this on purpose — and this is the number that proves it. That 900 is hardcoded in our own structure checker because it is qmd's chunk target, and step 4 reranks the best chunk, not the page. So "lead with a prose summary, keep a section under one chunk, surface synonyms in the body" stopped being style advice and became mechanically checkable invariants — purely because we took someone else's chunker seriously.
These constants were read out of the installed package, not the README — and two README figures were wrong: the rerank depth is 40, not 30, and there is no "15% overlap" (it is a 200-token window). Say the version, because these are implementation constants that can move. Stage 1 is the detail worth dwelling on: every stage here is expensive, so qmd's first move is to try BM25 and skip the LLM entirely when the keyword hit is confident — and passing an intent deliberately disables that bypass, because the obvious lexical match may not be what you meant. The payoff is the last line: the chunker's 900 is hardcoded in our own checker, and the reranker scores the best chunk rather than the page, which is why our authoring rules are checkable invariants rather than style advice.

What it actually costs to "always lead with search"

Measured on this laptop, this morning, against a 38-page wiki. Every agent in this system is instructed to start here.

CallWall clockWhere it goes
query · cold32.7 s16.1 s expansion · 1.7 s embed · 14.4 s rerank

vsearch11.4 sone embed, no expansion, no rerank — but the model still loads
search · BM250.13 sno model at all
  • 250× between the cheapest and dearest call. That spread is the entire justification for stage 1 — the BM25 probe exists because keyword search costs 130 ms and the LLM path costs tens of seconds.
  • Cold vs warm is not a caching detail, it's the usage model. A long-lived agent session amortises the model load; a one-shot CLI call pays it every time.
  • What this changes about our claims: the token saving is still unmeasured — but the latency cost is now measured, and it is not small. "Always lead with qmd" is a real trade, not a free win.
  • Caveat: single machine, one wiki, warm-vs-cold in separate processes. Directionally solid, not a benchmark.
The honest read: this is the strongest argument yet for the deferred query-time gate — and also the strongest argument for why an agent might quietly route around it. A discipline that costs thirty seconds on a cold call is a discipline people stop following. Which is exactly the behaviour our telemetry currently cannot detect.
This slide did not exist until qmd was installed on the demo machine — it is measured, not estimated, which is why it belongs in a talk that keeps complaining about unmeasured claims. The number to land is the spread: 130 milliseconds for BM25 versus thirty-two seconds for a cold hybrid query. Once you have said that, stage 1 of the previous slide stops looking like an optimisation and starts looking like the load-bearing design decision. Then close the loop back to part 3's second war story: we tell every agent to lead with the expensive path, we do not enforce it, and our telemetry cannot tell whether they complied. A thirty-second discipline is exactly the kind people quietly drop. Be scrupulous about the caveat — one laptop, one wiki, cold and warm in separate processes.
17Part 3 · Retrieval

Freshness has three owners — and none is redundant

A stale index is a silent failure: an ingest writes fifteen pages, the run dies before re-indexing, and every subsequent reader retrieves the old content with no way to know.
1 · The agent

Re-index as ingest step 10

The portable baseline. It is the only one that works for Codex, Copilot, or a plain CLI session — there is no server to do it for them.

2 · The orchestrator

Deterministic post-step

Fires after any clean ingester run. Covers the unattended path where nobody is watching. Presence-checks the binary and skips silently if it's missing.

3 · The git hook

Backgrounded after a merge

Only when the pull touched the wiki or docs. Covers a teammate's PR landing wiki changes outside any task flow.

The ordering is the design. The orchestrator's re-index runs after the run record is written, after the status hand-off, and after the next role is queued — so a slow index never delays the pipeline, and a failed index never flips a successful run to failed. But the outcome is amended onto the run record, so the failure is visible rather than silent. There is a real window where pages are new and the index is old; the mitigation is visibility, not a barrier.
It is unit-tested with an injected fake — five tests, no real binary, no API cost: fires once on a clean ingester run, never for another role, disabled by config, and a skipped index (binary absent) still lets the run complete. The failure path is coded but untested.
The framing that makes this land: three triggers is not belt-and-braces, it is three genuinely different write paths, and removing any one reopens a distinct hole. The ordering point is the engineering content — we deliberately made re-indexing non-blocking and then made its failure visible, which is the right trade when the alternative is delaying a whole pipeline on a two-minute embed. Admit the untested failure path; the skipped-binary case is tested, the throwing case is not.
18Part 3 · Retrieval

Two war stories

A · The global namespace — live, right now

Collection names live in a machine-global namespace. Five projects each registered a collection called wiki. Only the last-indexed owned it.

$ cat ~/.config/qmd/index.yml
collections:
  wiki:
    path: /Users/…/OtherProject/.tcgstackflow/wiki
  docs:
    path: /Users/…/OtherProject/docs

That is this laptop, today. Any project here that runs -c wiki searches that project's memory.

  • Originally caught by our own checker: 3 of 5 projects silently searching the wrong wiki. No error, no signal — just confidently wrong context.
  • Fix: qmd init → a project-local index. It changed only setup — names stayed stable, so zero edits to the six agent profiles.

B · Observe before you enforce

Search is mandatory at setup. At query time it is a discipline — and deliberately not gated.

  • The enforcement gate was fully built and unit-tested — then shelved. "Deferred" here means evaluated and held pending data, not "we ran out of time."
  • What shipped instead: every run records its discovery path — search, or index fallback — rendered as a badge. The condition that would justify merging the gate is written down as a measurable trigger.
  • The counter-objection was concrete: it adds a second concern (methodology, not risk) to the most safety-critical module, and it defends a bypass that no agent profile instructs.
And the postscript, because it is the honest half: that shelved branch is now 31 commits behind main, main has re-implemented the same files underneath it, and the classifier file picked up NUL bytes so git treats it as binary — no readable diff, no three-way merge. Re-enabling it is a rebase, not a cherry-pick. That is the real cost of shelving working code. Meanwhile the redirect counter it would feed has a schema, a serializer, a folding rule and a UI — and no producer. The meter was installed before the valve.
These two stories are what people will still remember next week, so give them room. Story A got much stronger the day qmd was installed on this laptop: the global config genuinely points both collections at another project, so this is not a recounted incident, it is the current state of the machine you are presenting from. If you are comfortable naming the project, put the real path up; otherwise leave it redacted — the point lands either way. It is the best argument in the talk for shipping a checker against your own dependency's failure mode: the bug is invisible by construction — no error, correct-looking answers, wrong project. Story B is the observe-before-enforce doctrine in its strongest form, because the gate exists and we chose not to merge it. Then the postscript, which is the bit most talks would omit: shelved code rots, and we can now measure exactly how much. If someone asks "so will you merge it?" — the honest answer is that the trigger condition cannot currently fire on a machine without qmd installed, and that is itself worth fixing.

The Cockpit is one process and a projection

  • geekstackflow ui spawns a zero-dependency Node http server on 127.0.0.1:4729, no auth, serving one Vue SPA. If the bundle isn't built it serves a ~50-line inline fallback UI against the same API — so npx geekstackflow ui works before anyone runs an install.
  • It must be local. A hosted backend cannot run your CLI, with your credentials, in your working tree.
  • Everything on screen is a projection of files: read layer → JSON → Vue. Transient run state is injected as an overlay on top — the read layer never imports the run manager, so the durable and the ephemeral stay layered rather than merged.

The action queue has no store

tasks.filter(t =>
  t.bucket === 'active' &&
  t.next_agent &&
  t.next_agent !== 'human')

over a nine-row status → role table: PLANNED → coder, IN_REVIEW → reviewer, IN_TEST → tester, VALIDATED → ingester.

Every "ready" badge you'll see in the demo is a regex over a Markdown Status: line. That's also why a manual status override is a real feature rather than a debug hatch.

Two honest notes: an unrecognised status falls through as itself — it isn't guessed at, it quietly drops out of the queue. And there is no cache anywhere: every request re-walks the registry, every task folder and every run record. That's why the "this needs incremental caching past 50 projects" note exists, written down and not yet built.
Set up the demo here. The single idea: the UI invents nothing. Every number, badge and queue row is derived from files on disk on every request, which is why you can edit a task file in your editor, hit refresh, and the queue changes. Then the two admissions. The no-cache one matters because our own design doc claims a cache exists and it does not — say the code, not the doc. And the fall-through behaviour is the right default: guessing at an unknown status would be worse than dropping it.

Pressing ▶ Run, exactly

claude -p "Adopt the coder role per .tcgstackflow/agents/coder.md and work on ES-6965.
      Read the task's two files under tasks/active/ES-6965/ and follow the coder procedure."
       --output-format stream-json --verbose --include-partial-messages
       --resume <latest session id>                       ← iterations 1–5 only
       --mcp-config /tmp/gsf-gov-<run>-<iter>.json          ┐
       --permission-prompt-tool mcp__tcgflow_governance__approve  │ 8 tokens,
       --permission-mode default                            │ governed runs
       --allowedTools Read,Grep,Glob,LS                     ┘

  cwd  = the worktree, or the project root
  env += GSF_WORKSPACE_DIR  GSF_CONTROL_URL  GSF_RUN_ID  GSF_RUN_TOKEN
  • No SDK. It is child_process.spawn('claude', …) in print mode, with the binary name injectable so the whole path is testable against a fake CLI.
  • No --model. No system prompt. No skill list. No project path. The role is indirection into a file — two sentences pointing at agents/coder.md, byte-identical to the "Copy prompt" string in the UI. All role separation, tool ceilings and procedure live in Markdown the agent is merely told to read.
  • --allowedTools here is not a sandbox — it is the pre-approved list. Everything not on it (Edit, Write, Bash, other MCP servers) is routed through the permission tool to a local gate. Governance is an allow/deny RPC, not confinement.
  • The runner adapter is 91 lines and pure — no filesystem, no spawn, no crypto. It only describes the invocation and maps the stream; the loop owns the spawn, the temp file and the token. That separation is what makes "adding Codex is a parse-and-argv adapter, not a rewrite" a credible claim rather than an aspiration.
This is the slide engineers photograph. Read the prompt out loud — it is deliberately anticlimactic, and that is the point: the agent's entire personality is a file path. Two things to emphasise. The allowedTools framing gets misread constantly: it is not a sandbox, it is the list that skips the gate. And the purity of the adapter is what makes the multi-tool story real — you can unit-test the six-iteration loop against a fake CLI replaying a captured stream, with zero API cost, because nothing in the adapter touches the world.

  • A "Run" is up to six claude invocations, not one — iteration 0 sends the role prompt, iterations 1–5 send a fixed continue nudge with --resume. Say the cost out loud before someone else does: a stubborn task can spend roughly six times a single invocation.
  • Two session ids are tracked. The first is identity; the latest is what --resume uses — because a resumed print-mode session can fork a new id, and resuming the original would silently drop everything in between. If you've built a resume loop against a streaming CLI, you have hit this.
  • The hand-off signal is a file read, not a stream event. After each iteration the loop re-reads Status: out of the task file. "The agent finished" is defined as it wrote IN_REVIEW to disk. Pure files-as-truth.
  • Other exits: abort · non-zero exit · single-shot ingest · no-progress, which is literally "the streamed transcript didn't get longer" — so an agent working silently through tool calls can look idle.
  • Tokens are summed only from result events, across every iteration, into one run record. Per-message usage is deliberately ignored to avoid double counting — a test pins this with a 999-token decoy.
  • Closing the tab does nothing. The only disconnect handler removes an SSE subscriber; a late subscriber gets the whole buffered stream replayed. The inactivity watchdog is re-armed on every chunk and suspended while an approval is pending, or "user at lunch" would kill the run.
Three details that signal real operating experience. One: resume follows the latest session id because print-mode resumes can fork — that is a bug you only know about by hitting it. Two: the hand-off is a file read, which is dogmatic files-as-truth and it is why worktree isolation took a whole design cycle to get right. Three: no-progress is measured as transcript length, which is honest but imperfect — an agent doing silent tool work looks stalled. Also land the cost point yourself: six invocations per run is the number a CFO would want to know, so don't let someone else discover it.

The approval modal is a blocked HTTP request

agent
calls a tool that isn't on the pre-approved list → Claude Code raises its own permission prompt
gate (local MCP)
classifies the call against governance.md. LOW / MEDIUM → allowed instantly, no human, no card.
gate → server
HIGH / CRITICAL → a blocking loopback POST with req.setTimeout(0). No idle timeout — it survives lunch.
server
verifies the per-run token, holds the socket open, and pushes an approval_request onto the run's event stream
browser
renders the card: Action / Risk / Why / Files / Rollback → you click
server → gate
the held response finally returns the decision · the tool call unblocks · the decision is written into the task log
This is not the Cockpit polling the agent. It is the agent's own permission prompt, redirected through the Cockpit — the subprocess is genuinely blocked inside a tool call the entire time, which is why the inactivity timer has to be explicitly suspended. And deny is not fatal: the gate returns "action deferred to human" and the run continues with everything else.
LOW
read, search, draft — just do it
MEDIUM
edit source, run tests — do it, log it
HIGH
install, push, PR, external writes — ask first
CRITICAL
prod deploy, destructive DB, force push — ask + rollback plan
  • A compound command takes the max of its segments — a trusted prefix followed by && rm -rf still classifies CRITICAL. Project rules can only raise; the trusted list only lifts HIGH→MEDIUM, never CRITICAL.
  • CRITICAL without a rollback acknowledgement returns HTTP 428 — from the route, not the modal. The task panel, the global inbox and curl all hit the same check. A UI-only guard would be theatre.
  • Precision: an unknown tool or a classifier throw fails safe (escalate to HIGH, ask a human). Only an unreachable intake fails closed (auto-deny). Those are different outcomes.
The hole, said before anyone finds it: if the temporary gate config can't be written to disk, the run spawns ungoverned — no permission tool, no tool ceiling — and the run record still stamps gate: mcp-intercept, because that value is a static adapter capability, not an observation that the gate attached.
The centrepiece of part 4, and the slide that matters most to the managers. The one line to land: a risky action physically stops mid-flight until a human decides in the browser, and it stops because the agent's own permission mechanism was pointed at us. For engineers, the fail-safe versus fail-closed distinction is the credibility test — most people say "fails closed" about everything; here escalating to HIGH is failing safe, and only a broken control channel auto-denies. Then volunteer the ungoverned-spawn hole. It is real, it is narrow, and disclosing it is worth more than the slide it costs.
23Part 4 · Orchestration

Isolation, concurrency, and what lands on disk

Isolation · per run

in-place · branch · worktree

Branch checks out tcgflow/<TASK-ID> in place. Worktree moves the child's cwd into a sibling directory and symlinks the search index in so wiki lookup still works. Both fail closed — a dirty tree fails the run rather than working on the wrong branch.

Concurrency

The slot is the lock

An in-memory map keyed on the resolved project path. No lockfile. One main-lane run per project, plus up to three parallel worktree runs. Consequence, stated plainly: two Cockpits on one repo have no mutual exclusion at all.

Crash

A placeholder record is the tripwire

A state: running record is written at launch; orphans are reconciled to aborted on next boot — deliberately only after the port bind succeeds, so a losing second instance can't mark the first one's live runs dead.

Chain — "run to completion"

planner → coder → reviewer → tester → ingester, launching the next role on hand-off.

  • A backward move is a bounce. The default tolerance is 1 — so one bounce is allowed and the chain halts on the second.
  • The halt writes a durable log entry that reclassifies it as a planning defect: "a task that keeps bouncing usually has an acceptance criterion that is ambiguous or untestable."
  • Every chained launch re-checks the budget — closing the gap where a queued run launches after the money is gone.

Persisted per run

runs/<task-id>/<run-id>.md
  role · tool · gate · session_id
  tokens: in · out · cache read · cache write
  state · started_at · ended_at
  git_base  ← baseline for the per-run diff
  isolation · branch · worktree_path
  embed · wiki_discovery · write_attempts
  + the raw transcript

The agent writes its own task-log entries. The server writes only structural ones — status safety-net, no-work, bounce halt, governance decision, PR approval, orphan reconcile — plus the human's manual override.

Move briskly — this is the "yes we thought about that" slide. The two lines worth saying deliberately: the lock is a JS Map in one process, so a second Cockpit or a hand-run CLI is invisible to it; and shutdown only reaps the main lane, so Ctrl-C with parallel worktree runs in flight orphans those children. Both are known, both are written down. The chain-bounce framing is the nicest idea here: instead of looping coder and reviewer forever, we cap it and reclassify the halt as a planning defect, which is almost always what it actually is.

25Honesty

Not enforced, and not measured

The project's posture is observe before you enforce, and earn every piece of complexity. A talk that hid these would be arguing against its own design.
Claim you might have heardWhat is actually true
Single writerProse, not enforcement. The permission gate is action-scoped, never actor-scoped — edits are MEDIUM and MEDIUM auto-allows, so a Reviewer can rewrite the code it's reviewing. What shipped is a write-attempt counter, whose trigger to act is a single occurrence. And even that badge can't render — the parser never surfaces the field the serializer writes.
Search-firstUnenforced at query time, by design. Worse: the telemetry is monotone, so it cannot distinguish "led with search" from "grepped first, then searched" — the exact behaviour the shelved gate targets.
Token savingsStill unmeasured. The skill says so in its own text: "discipline, not a proven saving." We count search calls versus direct reads, not tokens. The justification is recall — also unmeasured. The cost side, however, now is: 32.7 s cold, 1.2 s warm. We measured the price before we measured the benefit.
The structure gateCannot fail on quality. One fail-level finding exists in the whole checker. Fifty warnings exit zero.
Any tool, one workflowTrue for the workflow — the commands are portable Markdown. Not yet true for orchestration: only one runner is registered; any other value returns 501 at the launch door. The cost-spreading knob is real; the behaviour behind it is not.
Secure by defaultNo auth, loopback only — a documented single-local-user threat model, not an oversight. The per-run token protects only the three callbacks the child process makes. It is the reason a hosted version would be a different product, not a deployment option.
Do not rush this slide and do not apologise through it. Deliver it as the thesis: everything here is either enforced in code, or explicitly observed with a written-down condition that would justify enforcing it. The single-writer row is the sharpest — separation of duties is the organising idea of the whole workspace and it is the one invariant the enforcement layer never checks, and we know, and we shipped a counter instead. If someone pushes hard, the honest answer is that a role-aware gate is cheap to build and we are waiting for one occurrence in the telemetry to justify it.
Take away

One store.
Two retrieval layers.
Zero databases.

  • Memory is a git-diffable artifact. Every change to what the AI believes about the project arrives as a reviewable diff — no export problem, because there is nothing to export.
  • Retrieval is two-stage on purpose: statistical recall finds candidates, an authored graph bounds the expansion to one hop.
  • An agent is a subprocess with a Markdown file for a personality and a blocked HTTP request for a conscience.
  • Everything unfinished is written down — with the condition that would finish it.
The ask: take one real task through plan → code → review → test → ingest, and watch the wiki change in the diff. That single loop exercises every mechanism in this talk.

Close on the four lines, slowly. The subprocess line usually gets a laugh and it is also literally accurate, which is why it works. Then the ask, and make it small and provable: one task, end to end, and look at the resulting diff to the wiki.
